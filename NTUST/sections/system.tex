\chapter{System Architecture}
\label{sec:system}

Before delving into system details, this study first introduces the adopted system framework. To integrate the network Functional Application Platform Interface (nFAPI) with mainstream commercial equipment, the system proposed in this study adopts a stable two-stage split architecture. The network is first connected through the Split~6 nFAPI interface between network functions, and then converted to the standard O-RAN Split~7.2x interface to connect to a commercial Pegatron O-RU. Figure~\ref{fig:System-Architecture} illustrates this system architecture and its delay management mechanism.

\section{端到端架構}

\section{End-to-End Architecture}
\label{subsec:A_end_to_end}
This system establishes a complete 5G end-to-end communication link extending from the core network to the user equipment:
\begin{itemize}
\item \textbf{Core Network (CN):} The core component responsible for routing, session management, and user data authentication.
\item \textbf{O-RAN Central Unit (O-CU):} The logical node handling higher-layer protocol stacks, such as Radio Resource Control (RRC) and Packet Data Convergence Protocol (PDCP). It connects to the distributed unit via the F1 interface.
\item \textbf{O-RAN Distributed Unit (O-DU):} To optimize computational performance and deployment flexibility, the system divides the O-DU into O-DU High and O-DU Low. O-DU High executes as a Virtual Network Function (VNF) on virtual machines, while O-DU Low is deployed as a Physical Network Function (PNF) on dedicated hardware.
\item \textbf{Switch:} A commercial network switch located between the VNF and PNF. This intermediate layer connection utilizes the nFAPI protocol. However, traversing this packet-switched network inevitably introduces non-deterministic latency.
\item \textbf{O-RAN Radio Unit (O-RU):} A dedicated hardware unit responsible for Low PHY processing, Digital Beamforming, and Radio Frequency (RF) transmission.
\item \textbf{Commercial Off-The-Shelf User Equipment (COTS UE):} Standard commercial smartphones or modems acting as the network's terminal receivers.
\end{itemize}

\section{O-DU High: MAC, Scheduler, and Timing Core}
\label{subsec:B_odu_high}
Within the O-DU High virtualized network function, the timing control is organized as a unified timing control system. The core processes handling this timing core include the Scheduler, Node sync, and Delay Management:
\begin{itemize}
\item \textbf{Scheduler:} Responsible for allocating available radio resources (e.g., time-frequency resource blocks) and determining the exact priority and timing of downlink/uplink data transmission.
\item \textbf{Node sync:} Responsible for software-level clock synchronization. This procedure periodically exchanges synchronization timestamps ($t_1 \sim t_4$) with the PNF via standard \textit{DL/UL\_node\_sync} messages. It calculates the instantaneous clock offset and applies slot-level ($S_{adj}$) and microsecond-level ($\mu s_{adj}$) adjustments to align the VNF's local clock to the PNF baseline, eliminating long-term hardware clock drift (Clock Drift).
\item \textbf{Delay Management:} Operates on top of the stabilized clock phase established by Node sync. This mechanism utilizes the PNF Timing Info ($\Delta t_{arrive}$) feedback from the PNF to dynamically estimate transport network jitter. It then actively adjusts the slots ahead ($S_{\mathrm{ahead}}$) trigger offset of the scheduler. This control compensates for the non-deterministic packet transport delays and VNF processing delays without inducing synchronization loss.
\end{itemize}

\section{O-DU Low: High PHY and Timing Window}
\label{subsec:C_odu_low}
O-DU Low manages the High PHY baseband processing. At this level, the most critical synchronization mechanism is the nFAPI PNF Timing Window:
\begin{itemize}
\item \textbf{Timing Window:} A predefined and strict time interval. Let $T_{\mathrm{window}}$ denote the duration of this PNF timing window, and $T_{\mathrm{slot}}$ denote the subframe slot duration. When scheduling messages (especially \texttt{DL\_TTI.request}) sent by O-DU High traverse the network, they must accurately arrive and fall exactly within this window. Otherwise, the High PHY will reject the message, resulting in the inability to process data for that slot.
\item \textbf{Timing Info ($\Delta t_{arrive}$):} The PNF continuously monitors the exact timing info of control messages relative to the transmission deadline. This information is denoted as $\Delta t_{arrive}$, representing the remaining time margin within the timing window. The PNF periodically feeds this information back to the MAC layer for Delay Management. This establishes a closed-loop feedback control system to compensate for unpredictable transmission delay variations between the VNF and PNF machines.
\end{itemize}

\section{Timing Model}
\label{subsec:timing_model}
To formalize the delay-management problem, this section introduces the mathematical timing model of the nFAPI-based Split Option 6 architecture. Let $T_{\mathrm{slot}}$ denote the slot duration and $S_{\mathrm{ahead}}$ denote the number of slots by which the VNF scheduler triggers earlier than the target slot. For a scheduling message generated at VNF time $t_g$, the corresponding target PNF processing deadline is determined by the target slot boundary. The arrival margin reported by the PNF is denoted by $\Delta t_{\mathrm{arrive}}$, where $\Delta t_{\mathrm{arrive}} < 0$ indicates that the message arrives before the deadline (early arrival), and $\Delta t_{\mathrm{arrive}} > 0$ indicates a late arrival. Therefore, the delay-management objective is to select the minimum stable $S_{\mathrm{ahead}}$ such that late arrivals are avoided ($\Delta t_{\mathrm{arrive}} \le 0$) while the MAC HARQ Round-Trip Time (RTT) is not unnecessarily inflated.

\section{Key Verification Metrics}
\label{subsec:D_metrics}
To evaluate the stability, synchronization accuracy, and real-time performance of the proposed algorithm in non-ideal environments, this study defines the following key verification metrics:
\begin{itemize}
\item \textbf{MAC Layer HARQ RTT ($T_5 - T_1$):} Specifically measures the Hybrid Automatic Repeat Request (HARQ) loop delay at the MAC layer. This metric precisely reflects the feedback efficiency and operational health of the link layer.
\item \textbf{VNF-PNF Downlink Delay ($T_2 - T_1$):} Measures the accumulated one-way downlink latency from the virtualized machine (VNF) to the physical machine (PNF). This metric is used to directly quantify and analyze the delay jitter impact introduced by the intermediate Ethernet switch.
\end{itemize}
Note: RTT stands for Round-Trip Time. To verify the stability of the split architecture under non-ideal fronthaul conditions, this study simulates network delays using Linux Traffic Control (TC) on the uplink ($T_5 - T_4$) and downlink ($T_2 - T_1$) segments.

To validate the proposed performance optimization in a realistic network environment, the system design utilizes a commercial-grade deployment framework:
\begin{itemize}
\item \textbf{O-RAN Split 7.2x Interoperability.} \\
      Although the Small Cell Forum (SCF) has standardized the \textbf{network Functional Application Platform Interface (nFAPI)} \cite{douros2018nfapi} for the MAC-PHY split (Option 6), commercial Radio Units (O-RUs) natively support O-RAN Split Option 7.2x. To achieve seamless integration with open-source protocol stacks like OpenAirInterface \cite{wang2022opensource}, this system bridges these interfaces to ensure full-scale commercial interoperability.
\item \textbf{Hybrid System Architecture for End-to-End Verification.} \\
      To verify the performance of nFAPI in a fully commercial ecosystem, this paper adopts a \textbf{hybrid architecture} (Split Option 6 + Split Option 7.2). In this model, the system provides a Translation/Interworking Layer that enables the nFAPI-driven MAC/High-PHY to successfully interact with the commercial Pegatron O-RU. This setup allows the use of \textbf{Commercial Off-The-Shelf (COTS)} user equipment to verify nFAPI performance in a real-world end-to-end environment.
\end{itemize}
